# Smoke System Redesign

## Problem

The original smoke system required launching Project Zomboid and reading its
DebugLog to verify API surfaces exist. This is backwards — the full decompiled
PZ codebase (`PZCodebase/`) is available for offline verification, and the API
verifier (`verify_pz_api.py`) already cross-references every trait API call
against it. The DebugLog-based smoke gate added no value over what the offline
tooling already proves.

Meanwhile, in-game error detection relied on players encountering a broken trait
during normal gameplay — potentially hours into a save, mid-combat, where a
crash could cause real damage.

## Solution

Three layers with distinct responsibilities:

### Layer 1: Offline Gate (existing, unchanged)

`verify_pz_api.py` scans every `object:method()` call in UT trait Lua files and
checks each one against the decompiled PZ Java/Lua source in `PZCodebase/`. It
produces FAIL/WARN/OK for every call site. This is the hard pass/fail gate.

No changes needed. It already works and produces the inventory JSON that Layer 2
consumes.

### Layer 2: In-Game Startup Pings (new)

A Python generator (`tools/generate_smoke_pings.py`) reads the verifier's
`pz_api_inventory.json` and writes a Lua file
(`UniversalTraits/media/lua/shared/UniversalTraits/UT_SmokePings.lua`)
containing one unguarded call for every unique API surface the traits use.

**Purpose:** When a player loads PZ with the mod, every API surface gets a quick
ping at `OnGameStart`. If any API is broken (renamed, removed, returns nil),
PZ's native error handler fires a RuntimeException. Players using error
inspector mods see the problem immediately — before any trait runs in actual
gameplay. This is a pre-flight check that surfaces breakage early, preventing
save-damaging failures mid-session.

**How pings work:** Each ping is a bare call that discards its result. No
guards, no `pcall`, no `if` checks. If the API exists, the call succeeds
silently. If not, PZ throws an error in its standard format:

```
java.lang.RuntimeException: Object tried to call nil in runPings
```

The error inspector mod displays this just like any other game error.

**Dependency chains:** Some calls are chained (e.g. `player:getStats()` must
return something before you can call `:getEndurance()` on it). The generator
groups these: the root call is assigned to a local variable, and dependent calls
use that variable. If the root fails, dependent calls also fail — producing
multiple errors that all trace back to the same broken root. This is useful
diagnostic information, not noise.

**Deduplication:** Many traits call the same API. The generator deduplicates by
unique `receiver:method()` pair. The inventory reports ~220 unique surfaces;
each gets exactly one ping.

**Receiver resolution:** Most pings start from `player` (via `getPlayer()`).
Some start from globals (`getGameTime()`, `getCell()`, `ISEatFoodAction`, etc.).
The generator groups pings by starting receiver and sets up each one at the top
of the function.

**Example generated output:**

```lua
-- UT_SmokePings.lua
-- Auto-generated by generate_smoke_pings.py -- do not hand-edit.
-- Fires every PZ API surface used by UniversalTraits at startup.
-- If any call hits nil, PZ's error handler reports it immediately.

local function runPings()
    local player = getPlayer()
    local _

    -- player (IsoPlayer)
    local _stats = player:getStats()
    _ = _stats:getEndurance()
    _ = _stats:getFatigue()

    local _bd = player:getBodyDamage()
    _ = _bd:getBodyPartList()

    _ = player:getPrimaryHandItem()
    _ = player:getInventory()
    _ = player:getXp()

    -- globals
    _ = getGameTime()
    _ = getCell()
    _ = ISEatFoodAction
end

Events.OnGameStart.Add(runPings)
```

**Regeneration:** The gate runner calls `generate_smoke_pings.py` automatically
after the verifier produces its inventory. The generated file is committed to
the repo and deployed with the mod. It stays in sync with the trait code without
manual maintenance.

### Layer 3: Log Health Check (rewritten, informational only)

`tools/check_smoke_log.py` is rewritten from a smoke-marker checker to a
general DebugLog scanner. It finds the latest DebugLog and scans for UT-related
errors or warnings.

**What it looks for:**

- Java RuntimeExceptions with UT file names in the stack trace (e.g.
  `UT_actionhero.lua:13`)
- Lua errors referencing files under `UniversalTraits/` or `UTCore/`
- The `[UT_SMOKE]` prefix if present (backwards compatibility)

**Output:** A summary — error count, which files they came from, error messages.
JSON for the gate runner, human-readable for direct use.

**Gate integration:** The gate runner calls it and prints results, but the exit
code from this step **never** affects the gate's pass/fail. The gate summary
shows:

```
Live session health:         3 errors found (informational)
```

or:

```
Live session health:         clean (no UT errors in last session)
```

or:

```
Live session health:         no recent log found
```

## File Changes

### New files

- `tools/generate_smoke_pings.py` — reads inventory JSON, writes the Lua ping
  file
- `UniversalTraits/media/lua/shared/UniversalTraits/UT_SmokePings.lua` —
  generated, committed, deployed with mod

### Modified files

- `tools/check_smoke_log.py` — rewritten to scan for UT errors instead of
  `[UT_SMOKE]` markers
- `tools/run_update_safe_gate.py` — adds generate step, removes smoke
  manifest/coverage flags, makes log check informational (never fails gate)
- `tools/verify_pz_api.py` — removes `--require-smoke-coverage` and smoke
  scenario assignment logic

### Removed files

- `tools/pz_api_smoke_manifest.json` — no longer needed
- `UT_CORE/media/lua/shared/UTCore/UTCore_SmokeRecorder.lua` — no longer needed
- `UniversalTraits/media/lua/shared/UniversalTraits/UT_SmokeStartup.lua` —
  replaced by generated ping file

### Deployment sync

After generation, the ping file is copied to `release/` and the live mod folder
at `C:\Users\Admin\Zomboid\mods\UniversalTraits\`, same as any other Lua file.
The removed files are also deleted from release and live mod folders.

## Gate Pipeline

The unified gate (`run_update_safe_gate.py`) runs these steps in order:

1. **UT_CORE Lua tests** — pass/fail
2. **UniversalTraits Lua tests** — pass/fail
3. **API verifier** against PZCodebase — produces inventory JSON — pass/fail
4. **Baseline comparison** — pass/fail
5. **Generate smoke pings** from inventory — writes `UT_SmokePings.lua` —
   always succeeds
6. **Scan latest DebugLog** for UT errors — informational only, always succeeds
7. **Report summary**

The gate fails only if steps 1-4 fail. Steps 5-6 always succeed and provide
information.
